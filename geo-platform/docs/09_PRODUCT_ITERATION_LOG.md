## 2026-09-02 V1.1 Incremental Materialization Phase B

### Product Decision

Phase B 只解决 SourceClaim incremental materialization。昂贵计算单位不是
`SourceClaim` 行，而是一次 Passage SourceClaim extraction：

```text
Passage Semantic Input
-> ClaimExtractionMaterialization
-> 0..N SourceClaim rows
```

同一个 Passage 语义输入在同一个 `SOURCE_CLAIM_V1` contract 下只能完成一次昂贵
提取。重复 Run、重复引用、重复 passage row、重复执行当前主链，都不能线性增加
SourceClaim LLM 调用。

### User-Facing Rule

系统允许第一次补齐大量从未物化的 passage，但同一 Run Scope 立即第二次运行时，
SourceClaim LLM 调用应接近 0。若存在失败、stale 或无法确认的 legacy 对象，必须
能解释原因，不能表现成数百次重复计算。

### Implementation Rule

- `source_claim_materializations` 记录 SourceClaim extraction DONE / FAILED /
  stale 状态。
- `claim_count=0` 是合法 DONE，代表 LLM 成功判断没有有效 SourceClaim。
- materialization key 不包含 Run、Prompt、Evidence Package 或 SourceClaim row id。
- SourceClaim 行写入必须幂等；复用 materialization 可以为当前文档/passage 补齐
  SourceClaim 行，但不能重复插入同一语义 claim。
- 历史 SourceClaim 只在 prompt/schema metadata 和 SourceDocument snapshot metadata
  可确认时 lazy backfill，否则宁可重新物化。

### Boundary

本阶段不进入 EvidenceAlignment semantic cache、Binding-aware Recall、全链并发、
StrategyCandidate、Action、Experiment 或 Step 9。

## 2026-09-02 Current-Lineage Materialization And Evidence Review Groups

### Product Decision

当前单 Prompt 主链需要补齐 V1.1 上下文时，产品语义是：

```text
重新物化当前 Prompt / 当前 Run / 当前引用证据上下文
```

不是：

```text
全量重算所有历史正文、来源主张和证据关系
```

因此第 7 步出现“待生成 V1.1 输入”时，系统必须尽量只恢复当前链路缺失的

Prompt 的小范围恢复扩成历史库扫描。

### User-Facing Rule

证据审核按一组语义证据展示：

```text
AI 选择理由
+ 来源文档
+ 来源原文主张
+ 支撑关系
```

多 Run 下相同语义证据只需要用户确认一次。底层仍保留每条 Run-level
EvidenceAlignment，用于审计 run coverage / observed_run_ids。

如果主链重新运行后生成的是同一组语义证据，已确认状态应继承；只有新增或变化的
语义证据才需要用户再次确认。

确认一组证据成功后，页面必须重新读取后端审核队列作为唯一事实源。不能只在前端
本地删除一张卡片，否则删除第一组后第二组可能因为组件复用或旧 loading 状态而看似
一直等待，但实际上没有新的确认请求发出。

### Pitfall Recorded

`doc_id_filter=[]` 不能被当作“不过滤”。空当前引用范围代表当前链路没有可消费的

SourceDocument / SourceClaim 是文档级事实，可以跨 Run 复用；用户审核的是
“来源原文是否支撑这条 AI 理由”的语义关系，不是每个技术行 ID。重复 SourceClaim
ID 不应制造重复审核工作。

## 2026-09-01 Current Analysis Running State And Lock Visibility

### Product Decision

当前主链后台运行中时，第 7 步必须明确显示运行态或失败态，不能让用户点击确认/
重新运行后继续看到旧状态，从而误以为按钮无效。

### User-Facing Rule

当当前 Prompt 的主链后台任务正在运行：

```text

第 8 步 = 等待主链
```

当后台任务因本地数据库锁、异常或超时未完成：

```text

第 8 步 = 等待重新运行
```

人类审核按钮遇到本地数据库写锁时，必须返回清楚的中文提示，而不是静默失败或
继续显示“生成中”。

工作流状态接口只能展示当前主链状态，不能在刷新状态时现场执行 Citation Decision
重分析。生成/重跑必须由明确操作按钮触发。

运行中状态应尽量说明当前阶段，例如答案识别、正文补齐、来源主张抽取或证据对齐，
避免用户只能看到泛化的“生成中”。

单 Prompt 页面刷新主链路时，必须同时刷新工作流步骤状态。只刷新 Citation
Decision 数据会导致第 7/8 步继续显示旧的“主链运行中”，即使后端已经完成并进入
证据人工确认等下一道 Gate。

### Pitfall Recorded

本地 Alpha 使用 SQLite。长时间的 Evidence / Alignment 后台任务如果持有写事务，
会阻塞推荐事件确认、证据确认和状态刷新。后台任务必须阶段性提交释放锁，重复 URL
元数据缓存必须幂等处理。

前端也可能形成“假运行中”：后台任务已经完成，但页面没有重新读取
`workflow/status`，仍然使用点击重跑后留下的本地旧状态。所有主链刷新入口都必须
同步刷新当前 Prompt 的工作流状态。

证据人工审核必须按业务语义合并，而不是按内部 `SourceClaim` ID 展示。多 Run 或
重复抽取产生的同义来源主张，应在 UI 中显示为一组可批量确认的证据，同时保留
Run-level EvidenceAlignment 作为审计事实。

审核按钮必须以后端写入成功为准。若后端返回锁冲突或错误，前端不得提示成功、
不得移除待审卡片，避免用户以为确认生效但刷新后又恢复。

## 2026-09-01 Step 7 Single Strategy Channel Resolver

### Product Decision

第 7 步正式收口为唯一确定性 `Strategy Channel Resolver`。

```text
Capability Gap
Citation Decision Value
Channel Aggregation
Product Truth
Relevant Brand Asset
Retrieval / Citation State
Benchmark Evidence
↓
resolve_strategy_channels(...)
↓
primary_intervention_path
planned_channels
channel_roles
channel_rationales
```

Capability Gap、Citation Decision Value、Channel Aggregation、Product Truth、
Brand Asset 和 Retrieval/Citation State 都只是 Resolver 输入，不再各自产生另一套平台结论。

### Why

上一版已经让 Step 7 消费 Citation Decision Value，但平台角色仍容易被理解为两套规则拼接：

```text
CONTENT_GAP -> 官网 PRIMARY
Citation Decision Value -> 知乎 SECONDARY
```

这会导致两个问题：

```text
1. 官网 PRIMARY 的依据容易被误解成“官网天然优先”。
2. EVIDENCE_GAP 下第三方 Decision Citation 即使很强，也可能被旧规则压成 SECONDARY。
```

本轮修正为同一个 Resolver 统一解释：

```text
CONTENT_GAP
-> 一方资产可 PRIMARY

EVIDENCE_GAP + 强第三方 Decision Citation
-> 第三方渠道可 PRIMARY

DISCOVERABILITY_GAP
-> Retrieval 扩展优先

PRODUCT_GAP
-> Product Improvement，不包装成内容渠道

UNKNOWN / NO_GAP
-> 不强行生成 PRIMARY
```

### User-Facing Rule

## 2026-08-25 Workflow State Integrity

### Product Decision

Single Prompt workflow must be one integrated product chain, not a set of
parallel modules:

```text
采集样本
-> 答案决策识别
-> 目标品牌事实
-> 引用证据
-> 对标来源
-> 缺口诊断
-> 推荐动作
-> 实验草案
```

Citation Optimization Decision V1 belongs inside this chain. It may have a
detail page for inspection and operations, but it must not appear as a separate
homepage module competing with the main workflow.

### State Ownership Rule

Each workflow card has exactly one primary fact source:

| 阶段 | 唯一主状态源 |
| --- | --- |
| 采集样本 | 当前 Prompt Runs |
| 答案决策识别 | RecommendationEvent / Answer Semantic |
| 目标品牌事实 | Product Truth |
| 引用证据 | 当前 Prompt Evidence Package + SourceDocument / EvidenceAlignment |
| 对标来源 | Citation Decision V1 Benchmark derived state |
| 缺口诊断 | Source Gap derived state |
| 推荐动作 | Current Gap -> Proposal |
| 实验草案 | Current human-confirmed Strategy / Plan / Experiment |

Legacy workflow outputs such as `continueResult` may be displayed as historical
execution context, but they must not mark the current Citation V1 chain as
complete.

### Context Identity Rule

Decision data must be bound to the current analysis context:

```text
project_id
prompt_id
evidence_package_id
analysis_version
```

The frontend must discard decision results whose `prompt_id` does not match the
current Prompt. Prompt switching must clear Prompt-scoped Citation Decision,
benchmark, proposal, channel, action, and experiment state before reloading.

### Change Warning Rule

Any future change that alters the main chain order, creates a new top-level
module, or changes a card's primary state source must be treated as a product
level change. It requires an explicit development-log entry and product
iteration-log entry before implementation.

### Answer Decision Repair Rule

The second workflow step, `答案决策识别`, must be repairable from the decision
diagnosis detail page when machine-recognized answer objects are blocked by
validation failure or unknown entity relationship.

The repair surface is not the generic empty review queue. It must show the
actual answer-decision objects and let the operator choose:

```text
确认为竞品
设为目标品牌
不进入决策
```

Only confirmed target-brand or competitor objects can count as valid
answer-decision events. Rejected objects are audit records, not valid choice
events, and must not advance Product Truth, Citation Evidence, Gap, Action, or
Experiment.

The workflow must distinguish:

```text
all_reviews_done
= 当前审核队列已清空

ready_to_continue
= 可以继续生成缺口和动作
```

A Prompt can have `all_reviews_done = true` while `ready_to_continue = false`
when the only detected answer objects are validation-failed or rejected. In that
case the UI must route the operator to answer-decision repair, not to Gap /
Action generation.

### 2026-09-22：目标品牌事实从“流程门禁”收敛为“声明资格”

答案信号、目标品牌事实、策略方向三者正式分离：外部能力信号不再伪装成跨品牌 Truth 覆盖关系；

Step 7 结合有效 Evidence、当前关联缺口和可验证渠道判断，具备能力不等于必须强调，更不等于渠道
已经有效。

reprojection，Answer 与 Evidence 原样绑定、外部调用为 0，并要求用户只复核新的事实关系。事实未齐
不会阻断继续分析回答和引用资料，只限制依赖它的确定性策略声明和 Step 8 公开内容。

同一段答案同时将目标品牌和其他工具列为选项时，不能把共享理由再次显示成一个独立的“外部能力
缺口”。目标品牌推荐继续进入目标品牌 Reason→Truth；其他工具改为“同段共同推荐选项”，只描述
竞争环境，不重复出现事实核对入口，也不作为另一条目标适用性依据。只有没有同段目标品牌 Reason 的
外部能力，才保留为独立能力核对线索。
