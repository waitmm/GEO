# 运行可用性与数据边界

文档编号：PRD-OPS。里程碑：M0。版本：2026-10-09。实现状态：部分实现及隔离验证，完整发布验收未完成。

业务依赖：基础能力，无前置业务模块。共用规则见 [数据与状态契约](16_共用契约与状态.md)。

## 目标与范围

确保任务状态可信、数据持久、可恢复且不串项目。基于现有架构实现，不新增与当前交付无关的微服务、Runtime 或权限体系。生产是否就绪由实际部署核查和恢复验证决定，本文件不宣称现有代码已满足。

## 页面和主要操作

任务中心或现有等价入口展示真实任务状态、阶段、覆盖、错误与恢复操作。只向用户展示有用信息；请求追踪、版本和耗时可在详情查看。凭证只显示是否配置，不回显密钥。

## 正常流程

1. 按仓库真实配置启动服务、迁移与任务执行组件。
2. 写入操作校验项目/用户边界、当前版本和幂等键。
3. 任务状态持久保存；刷新、断线和重启后从后端恢复。
4. 错误记录具体阶段与可恢复动作，保留已经完成的数据。
5. 发布前完成现有架构的备份恢复、启动和主要业务路径验证。

## 输入输出与业务字段

| 字段/对象 | 要求 | 语义 |
|---|---|---|
| job_id / project_id / owner_scope | 必需 | 访问、查询、写入均检查归属 |
| idempotency_key / base_version | 相关写操作必需 | 提交与重试不得重复执行 |
| error_code / recovery_action | 异常必需 | 业务限制与基础设施错误分开 |
| usage / elapsed_time / provider_request_ref | 可得时记录 | 不存明文凭证，不将无日志等同于零成本 |
| backup / migration / deployment_evidence | 交付留档 | 真实环境及结果，不预填通过 |

以上是业务信息要求，真实表和接口复用映射由 M0 完成，不强制按字段新建一套模型。

## 需求与规则

| 需求编号 | 行为要求 | 可观察标准 |
|---|---|---|
| OPS-001 | 后端状态是权威，GET 查询不得触发分析或写业务数据。 | 前端状态不能从旧 Prompt 结果推断当前成功。 |
| OPS-002 | 任务输入及结果严格项目隔离。 | 猜测其他项目 ID 不能读写数据。 |
| OPS-003 | 采用当前已选技术基线并核查真实运行值。 | 既有单机 SQLite/WAL/单 writer 等约束以代码证据核实，不另建第二条业务主链。 |
| OPS-004 | 迁移、备份和恢复应有可执行说明。 | 不为错误派生结果增加长期兼容；清理按明确对象与可恢复方式执行。 |

## 状态和异常

应用启动、任务执行、外部服务和数据存储分别记录健康情况。等待凭证、限流、模型响应非法和程序错误分开。预算耗尽不能继续隐式付费调用；有授权范围则按既有规则执行，不新增每一步人工确认。

## 验收场景

| 用例 | 需求 | Given | When | Then |
|---|---|---|---|---|
| AC-OPS-01 | OPS-001 | 系统已有结果 | 连续刷新和查询 | 不创建新分析、发布记录或外调。 |
| AC-OPS-02 | OPS-002 | 当前身份/项目 A | 请求 B 的对象 | 拒绝或不可见，不返回 B 内容。 |
| AC-OPS-03 | OPS-001 | 任务已有阶段结果 | 重启服务并继续 | 状态与范围恢复，不出现重复成功产物。 |
| AC-OPS-04 | OPS-004 | 可用备份及迁移脚本 | 在隔离环境恢复 | 能读回配置、范围、结果和发布/复测关联；记录实际证据。 |
| AC-OPS-05 | OPS-003 | 真实启动配置和数据库可访问 | 执行 M0 检查 | 记录实际技术栈、数据库设置、写入模式与迁移值，发现偏差时明确修复而不建第二主链。 |

各场景初始状态均为 NOT_RUN。验收结果填写到 [验收矩阵](17_验收矩阵.md)，不得因文档齐全就标为通过。

## 当前运行入口与恢复约束

- API：`app.release_main:app`；worker：`scripts/release_worker.py`；页面默认 release 模式。
- 代码及本机正式库迁移版本为 `20261009_01`（2026-10-09 已执行保护性升级）。启动只验证版本；在 backend 显式执行 `.venv/bin/python -m alembic -c alembic.release.ini upgrade head`。
- `GEO_RELEASE_DATABASE_URL` 指定独立数据库；不得把旧开发库当正式库。
- 一个 API、一个 worker，同机 SQLite。worker 使用数据库旁 OS 文件锁排除第二进程，并写独立心跳。
- API 重启不再恢复任务。worker 取得独占锁后调用既有恢复函数，不抢占仍在执行的业务。
- `/api/health` 分开报告 API 和 worker；心跳不代表业务成功。
- 每日采样固定问题原文、时区、时间、数量及总尝试上限。暂停不伪造运行中任务取消。
- 验证码、登录失效或会话隔离失败时，后续 Run 记为未执行受阻并停止调用；恢复不重置额度。

## 访问与私有数据

未配置邀请凭证时只允许真实 loopback 客户端及 localhost/loopback Host。本机模式不得经反向代理开放公网。

远程部署必须使用 HTTPS，并以 `GEO_RELEASE_ACCESS_CONFIG` 指向 `0600` 权限 JSON 文件。受控邀请记录名字、随机凭证 SHA-256、管理员标记和明确 project_ids；不存明文密钥，不建立 SSO。管理员创建项目，普通操作员只能访问授权项目。

生成新配置（目标必须不存在，禁止提交 Git）：

```bash
.venv/bin/python scripts/release_invite.py --config release-access.json --key-file release-invite.key --name owner --admin
```

Cookie 为 HttpOnly/SameSite，远程 Secure，有效期8小时。会话仅在单 API 内存保存，重启需登录。权限文件变更即时生效，不重算业务结果。代理只能信任明确上游，不能接受任意转发头。写请求检查 Origin，登录限速；业务 API 统一授权后仍做对象归属校验。

控制台响应 `noindex`、`no-store`，它们不代替鉴权。权限单测不等于全面渗透测试或公网发布验收。

## 备份与验算

使用 SQLite Online Backup API；正文、完整机器输出和采样 artifact 按明确根目录归档：

```bash
.venv/bin/python scripts/release_backup.py --database geo_release.db --output backups/unique-backup --artifact-root artifacts
.venv/bin/python scripts/release_backup.py --output backups/unique-backup --verify
```

输出目录必须新建。验算 DB 完整性、外键、Snapshot 文件及正文 hash；清单记录归档根目录。密钥和浏览器登录 profile 不自动归档。复制中内容变化会失败，不能宣称成功。

恢复必须在隔离目录验证数据库、审核/版本与文件路径对应，不覆盖正式库。

```bash
.venv/bin/python scripts/release_upgrade_check.py --backup backups/unique-backup --output backups/unique-isolated-restore
```

2026-10-09 已完成：`backups/delivery-20261009-full-before-migration` 备份数据库、109份来源文件绑定和1460份 artifact；`backups/delivery-20261009-isolated-restore-verified/upgrade-report.json` 验证恢复文件、hash、外键及迁移后41张历史业务表逐行指纹不变。正式库随后显式升级，同样核对41张旧表指纹不变，新增3张表均为空。应用实际 DB-API 为 SQLite 3.51.3、WAL、foreign_keys=1。API重启健康检查通过，worker未启动。

该证据不包含凭证/浏览器profile恢复，也未验证更换部署根目录后的路径重定位。完整干净部署与三条产品E2E仍未完成，不能将备份成功等同于最终发布验收。
