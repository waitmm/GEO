## 里程碑

| 里程碑 | 交付内容 | 退出条件 |
|---|---|---|
| M0 开工核查与基础契约 | 能力复用图、真实技术基线、范围/版本/任务状态 | 已确定现有入口及最小改动；身份和恢复基础具备实施证据 |
| M1 Monitor 可用 | 品牌/Prompt、采样池、指标、机会入口、来源快照 | 用户能从真实样本看到可信指标并选定优化范围 |
| M2 Optimize 完整交付 | 自动分析、事实边界、策略、稿件、QA、可选纠错 | 无人工审核和无完整知识库也能交付针对性行动 |
| M3 独立 Validate | 固定基线、新采样、可比性与变化报告 | 无发布前置，也能如实比较；实际发布仅是可选历史证据 |
| M4 正式验收与交付 | 三类场景、真实闭环、启动恢复证据 | 主路径与边界用例通过，无冒充已完成的未测项 |

以上为产品里程碑，不是五套独立主链。可根据真实模块边界开展互不冲突的工作，但接口与数据依赖必须明确；本包不自动授权启动多 Agent 并行修改。不要等所有页面精装修完成才验证主链，也不要跳过产品入口只交付脚本。

## 状态规则

READY：依赖满足，可开始；WAITING_DEPENDENCIES：前置任务未完成；IN_PROGRESS：正在实现；BLOCKED：出现明确阻断；IN_REVIEW：实现和自验已完成，待交付检查；DONE：完成标准及验收证据齐全。

每项任务记录负责人姓名、预计工作量和开始/完成时间，当前未核查代码故不预填。M0 后由实际负责人估算，区分复用接入与新开发；不要拿文档页数推算工期。阻断必须写具体原因、影响范围和下一步，而不只写“待定”。

## 单任务完成标准

1. 实现满足关联需求；未改动范围明确。
2. 对应验收场景已实际执行，记录输入版本与结果位置。
3. 涉及状态、身份、外调或数据更改的风险有针对性验证。
4. 没有把假数据、测试替身或模拟发布结果写成真实成功。
5. 更新任务台账、实现映射和必要操作说明；有仓库时记录提交/PR。

产品负责人验收输出针对性与使用流程；开发负责语义正确、接口和状态；验收人员验证场景及回归。软件验收中的人工检查不等于产品每次运行都要人工审批。

## 管理节奏

每个工作批次开始时选择依赖已满足的任务，结束时更新完成项、证据、阻断和下一项。优先解决阻断当前主路径的问题。新增想法进入后续版本清单，只有真实错误、交付阻断或范围冲突才重开冻结决策。

不用反复要求负责人审批已经明确授权的日常修复；真实外部发布、额外付费调用和破坏性数据操作遵循当前会话/项目的既有授权范围。
