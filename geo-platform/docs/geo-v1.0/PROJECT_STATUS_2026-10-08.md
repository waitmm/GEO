## 1. 总结

**产品目标已经明确：围绕一个 Prompt，完成 Monitor → Optimize → Validate。当前已有较厚的采集、来源、语义分析、版本和安全基础，也形成了一条真实单 Run 的策略与稿件记录；但尚未完成真实发布后的复测闭环，也不能把当前稿件生成和 QA 认定为成熟通用能力。**

必须区分三种完成：

- 有代码和隔离测试，不等于正式产品操作已验收。
- 有真实输入和保存结果，不等于所有关系判断正确或产品能力通用。
- 有策略和稿件，不等于用户已发布，更不等于品牌表现改善。

当前更准确的阶段是：**单 Prompt / 单 Run 正式交付验证阶段，已到稿件与有限 QA，尚未完成发布、复测和效果观察。** 不报没有依据的“整体完成百分比”。

## 2. 产品到底是什么

面向品牌负责人、内容运营和增长人员的生成式搜索优化产品。不是只看排名的监控面板，也不是需要用户逐项给模型结果打标签的分析工作台。

| 产品部分 | 用户的问题 | 应交付的结果 |
| --- | --- | --- |
| Monitor | AI 在这个问题里怎么呈现我和其他选项？ | 回答、提及/选项/推荐、引用、覆盖和未知范围 |
| Optimize | 我应该改什么，为什么，具体怎么做？ | 有依据的方向、资产与渠道建议、具体稿件/修改稿、QA、执行条件 |
| Validate | 实际执行以后发生了什么？ | 固定基线与新样本的同口径变化、分子分母、可比性和限制 |

价值来自把真实回答、可消费来源、品牌实际能力和具体行动连起来，再用新采样观察变化。不能证明 AI 内部生成因果，不能保证被引用，不能承诺一次行动导致提升。

当前产品原则：

1. 一个 Prompt 是一个完整问题，各 Run 是该问题的一次回答，不把平台生成的搜索词当成多个 Prompt。
2. 复用成熟采样、抓取、计算和缓存能力；由 V2 负责业务身份、状态、版本和正式入口，不复活旧工作流隐式状态。
3. 知识库和分析型人工审核不是自动分析的普遍前置条件。无品牌事实也应能输出受约束的探索方向，不能编造品牌能力。
4. 主链是否继续计算，与单个事实、关系或稿件是否可用于特定用途分开。
5. 内部探索方向、可执行稿件、公开品牌声明的资格不同，不能互相自动升级。
6. 人工负责实际业务信息、纠错、权限和发布；Quality Lab 的人工校准不是所有用户的日常必经环节。
7. 不把来源被引用等同于支持理由，不把文本对应等同于证明模型实际采用，更不把来源声称等同于目标品牌已核实事实。

这些是当前交付目标，不表示每项都已实现到位。

## 3. 完整主流程

```text
项目/品牌配置 + Prompt
  → 采样记录池（已有样本可复用，也可继续采样）
  → 用户明确选择 run_ids
  → Analysis / Context 固定范围
  → Citation Manifest 固定原回答引用
      ├─ Answer Semantic / AnswerUnits
      └─ 自动正文获取 → 人工补录/明确处置 → Source Completion
  → Citation Contribution / 证据关系
  → 按用途检查品牌事实与对象资格
  → Strategy：观察、问题、假设、行动及限制
  → Asset/Channel 决策：类型、目的地、新建/更新/条件方案
  → 实际稿件或页面修改稿 → 自动 QA → 必要修复
  → 用户实际执行并登记发布
  → 发布后的新采样
  → Validate：同口径比较与归因限制
```

### 3.1 冻结不是禁止继续使用

冻结的是“这次结果究竟用了哪批输入”。用户仍可继续采样、补正文、更新品牌事实；可以继续看旧分析，也可以显式创建新分析或派生新结果版本。新增内容不应悄悄改变已经引用的旧结果，也不应迫使所有已有计算重跑。

### 3.2 来源与 Answer 不必互相等待

引用范围先固定，Answer 和正文准备可分别推进。证据计算消费精确的回答版本、正文版本和对应资格。人工放弃来源只形成限制，不产生支持/不支持。处理完所有来源也不代表证据充分。

### 3.3 产品自动化与现实业务授权分开

系统应自动完成可计算的分析和方案，不要求用户先替系统选资产/渠道。但账号控制、可编辑权限、真正发布、额外付费调用和新采样仍需真实信息或授权。未知信息必须显示未知，不能靠自动化虚构完成。

## 6. 本次核查必须明确的实现问题

### 6.1 稿件有场景硬编码，违反通用交付目标

`backend/app/modules/single_prompt_v2/execution.py`：

- `_target_brand_snapshot` 包含短链、私信卡片、外链、追踪等固定功能词列表。
- `_safe_delivery_sections` 根据“短链”“小风车/直播间”“私信/卡片”选择固定正文。
- `_build_publication_draft` 固定使用跳转场景、抖音检查、短链/私信/直播结论，并固定“三种”路径标题。

因此，本例有正文不等于换一个 Prompt 仍能生成正确、具体且有依据的稿件。这不是需要再搭平台，而是现有交付器没有完全兑现“显式输入驱动、通用主链”的要求。

### 6.2 QA 深度和修复证据不足

`_delivery_qa` 的 Prompt 针对性主要检查关键词出现；正文完整性检查标题、章节和结论；来源绑定主要检查 ID/片段存在；风险识别主要依赖有限正则。它没有全面证明每条公开陈述被来源实际支持。

`repairs` 还固定返回三项 APPLIED，不能把这种静态列表当成逐次发现问题并实际修复的完整证据链。应区分确实修改了什么与模板本来就如此。

### 6.3 当前编译输入仍有可变读取

`_compile_machine_delivery` 根据固定项目/Prompt ID 读取当前 `Project`、`Prompt`，并按 Context 查询快照，再参与品牌页选择和稿件编译。这不等于已证明重放时完全只消费冻结 DTO；配置变化后可重复性需要收紧。此处没有证据说明当前真实原文被改写，不应把实现风险说成已经发生数据污染。

### 6.4 来源贡献不能回答生成因果

22 个 Binding 不是 22 个已证明的模型生成依据，更不能直接除以引用数量形成“真实使用率”。召回覆盖、评估完成率、内容支持率、明确引用锚点和生成影响是不同指标。`UNPROVEN`、`UNAVAILABLE` 仍需保留。

### 6.5 产品入口与进度表述欠账

此前空白页是开发入口仍指向 legacy 界面/API，与正式 release 页面不一致。最近已修复，不能只说“用户没有找到入口”。当前产品仍需要统一已有结果、运行中状态、下一步操作和实际限制的表达，不能靠内部 ID 或状态英文让用户自己拼主链。
